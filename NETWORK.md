Adding or widening a call is a privacy-sensitive change, and this file changes in the same pull request.

## Demo worlds

A demo world (0.7.0, choice D8) connects, on the phone and on a PC, only to the demo server, `https://minhajna-demo.djazair.dev`, which the project runs ([the server's README](apps/server/README.md)). The only other part of the app that connects is [the directory](#the-directory), on the same server. Answer 570 sets the rules:

- **A guard on the app's connections.** The app's first import wraps the global `fetch`, `XMLHttpRequest` and `WebSocket`, and on a PC `EventSource` and `navigator.sendBeacon` too (`apps/android/src/network/guard.ts`). Each refuses any address but the demo server, and the demo server too unless a world is open or the path is [the directory's](#the-directory). On a PC, the page's own files stay open, and its security policy allows no other address; Android's debug builds keep Metro on the developer's computer. The globals do not cover React Native's native image loading, its networking and socket modules imported directly, or a native module's own requests, so the app uses none of them: a test reads the code and fails if it finds a remote image, such a module, an HTTP or socket call in the app's Kotlin, or a WebView that does not block network loads.
- **One client.** Only the world's client (`apps/android/src/network/world-network.ts`) sends to a world's paths on the demo server: to start the open world, or to that world's own paths. Each request carries the world's ID and its pass, which the device works out from the world's code; the code's secret never leaves the device. No cookie, cache or referrer goes with it, and it stops after 20 seconds. In a browser a redirect fails it; on Android, React Native follows a redirect itself, with the pass; the demo server sends none. An answer longer than 1 MiB, or one that comes after the world was left, is dropped.
- **Which pages may call it.** In a browser, the demo server answers only the PC web app's own origin, `https://minhajna.djazair.dev`, the hosted test's, `https://minhajna-test.djazair.dev` ([the demo host guide](docs/demo-host.md#the-hosted-test)), or `http://127.0.0.1:4180` and `http://127.0.0.1:8787` when it is tried locally, and the dashboard app's, `https://minhajna-admin.djazair.dev`, `https://minhajna-admin-test.djazair.dev`, `http://127.0.0.1:4181` and `http://127.0.0.1:8788` (answer 855), for the methods and headers the world's client sends, and never with cookies or other credentials (answer 583). A page elsewhere cannot read its answers.
- **What a world sends.** Its keys, sealed under its code, with its date; each space's sealed batches of exactly one size; and requests to certify a signing key the device made for that world. All of it is made up: a world never holds the teacher's own records, which stay shut while it is open (#558). In a teachers' world, its starter opens the world's observatory as the world starts (`POST /worlds/<ID>/insights`), holding made-up sendings from classes that do not exist, in as many requests as they take, or one request holding none when the start has no reference data. Once its teacher turns on the anonymous insights (#622, answer 697), and while the world is open, each term's end sends one sending for each class that follows a plan pack (`PUT /worlds/<ID>/insights/sendings`), the same text the world's insights page shows for that term: its format, a random ID for the class and term, the term's random token, the school and term's code, which the server, on receipt, replaces with a mark to count schools, the school year and term, the wilaya, grade and subject, the pack and release, the sessions on each item, the items merged, skipped, split or re-taught, and how far the class got. It holds nothing that identifies a teacher, a pupil or a session, and no date or reason. The world's store keeps each sending as sent. The server erases each world on its 7th day. One call carries the teacher's own words: a problem report, only when the teacher presses to send it to the world's operators ([Problem reports](#problem-reports)). A later call is added here in the pull request that adds it.
- **The world's date.** Every device in a world reads the date once a minute while the world is open (`GET /worlds/<ID>/date`, #630, answer 724), since only the device that moves it would otherwise see it move. The request carries nothing but the world's own pass, and the answer is the date and the world's announced days.
- **The pack editor's lifecycle (#612).** The curator and Ministry demo flows use the world's keys already held in memory, check `GET /worlds/:world/date`, read the national space, and put signed source-pack drafts and lifecycle changes on an opaque stream there, through the same `PUT /worlds/:world/spaces/national` and `POST`/`GET` batches calls. Every uploaded batch is 4,124 bytes; one whole change fits at most 128 batches and is refused before upload if it is larger. Source text stays inside the ciphertext. No teacher record, pupil data, code secret or unsealed key is sent. The device checks the world and signatures, and a damaged or incomplete authoring history blocks another write. A demo Ministry publication is marked Official only inside its world: real mode and another world refuse its file. It adds no new address. Each change first takes its step under the role's pack-editor account, `POST /worlds/:world/packs/steps`, which carries the release's name, stage and status and a digest keyed with the world's sealing key, never the release; a device signs in with `GET /worlds/:world/packs/account`, and the device that started the world makes the accounts with `POST /worlds/:world/packs/accounts`. Readers fetch the world's CA key with `GET /worlds/:world/ca` to check each step.
- **Plan-error reports in a world (#616).** A teacher in a national world can report a plan error to its curators. Only when the teacher presses Send, the device puts the report on another opaque stream of the national space, through the same batches calls, sealed under a key from the world's sealing key, at the same 4,124 bytes a batch. It holds the pack and item IDs, the release, the kind, the note, the world's date, and a name only if the teacher turned credit on, and nothing about a class, school or device. The server can't read it; anyone holding the world's code could. A teacher moving a class to a new release (#617) sends nothing: the move stays in the world's own store on the device.
- **What the server sees.** It reads the device's IP address only to count its rate limits, in memory, and never logs or stores it; requests are never logged. In front of it, Cloudflare sees each request's IP address and browser, under its own policy, as for the PC app, and a Worker of the project's hands each request on, keeping no log. A container that has had no request for about 30 minutes sleeps, and the next request wakes it from its archive; Cloudflare's own schedule wakes it once a day for the sweep, which sends nothing of anyone's ([the demo host guide](docs/demo-host.md#how-it-runs)).
- **What the observatory reads.** In a teachers' world, the observatory's Reports page on a PC (#627, answer 680) reads a term's figures only once the world's date has reached that term's end: first the packs they cover (`GET /worlds/<ID>/insights/figures?year=&term=`, with the school year and term), then one pack's figures at a time (the same with `&at=`, the pack's place among them). The figures come back already added up, the nation's and each wilaya's, every figure under its floor hidden by the server. The device that started the world, holding its starter token, ends that term's collection when the page finds it still open or still being formed (`POST /worlds/<ID>/insights/closed`, with the starter token and only the school year and term); ending it again changes nothing. The teacher's comparison of a class with its peers (#623, answer 700) reads the same figures for that class's pack, on a phone or a PC, and is worked out on the device, the starting device ending the term the same way, once what is due has gone if taking part is on; if that fails, the term stays open and nothing is read. Nothing else is sent, and none of the class's figures, though the pack it asks for by place tells the server which pack this device looks at. A sending the server then refuses for that ended term is read as late: the device reads the figures once more to tell it from any other refusal.

## The directory

The directory is the part of the demo server that lives outside any world and is never swept (answers 802 to 809): the Ministry's reference list, each school's book, and joining a school. Every name in it is made up until the national system exists. Only the directory's client (`apps/android/src/network/directory-network.ts`) calls its paths, and the guard keeps them open outside a world only as plain segments under `/directory/`, so no dots or escapes can lead anywhere else on the server. No cookie, cache or referrer goes with a request, no world's pass, and it stops after 20 seconds. In a browser a redirect fails it; on Android, React Native follows a redirect itself, with whatever the request carries; the demo server sends none. An answer longer than 1 MiB and a little, which holds the largest document the server takes, is dropped. The container sleeps, and the host answers 503 while it wakes, for about 45 seconds, so the client asks again, for about a minute and a half at most, and lets the page say so; once the server has said it wakes, a read or a join that had no answer in time goes again too.

What each page sends:

- **The reference list.** During setup's first step, and when Settings changes or adds a school, the phone reads the published list whole (`GET /directory/reference`), holds it in memory while that screen is open, and keeps only the school chosen. The request carries nothing: no code, and nothing of the teacher's. The level, option, wilaya, commune and school are chosen on the device, so the server never learns which. Setup therefore needs the network. With none, or with nothing published, the step says so and offers a retry.
- **Joining the school.** From Today, while no class has arrived, and from a school's rows in Settings, to join it or fetch its update, the phone sends the joining code the school gave the teacher (`POST /directory/join`, `{code}`) and nothing else: no name, no record, no other code. The answer, the teacher's classes, pupils and sessions as the school's book has them, stays in memory until the teacher approves it, then becomes records on the phone like any other. The code is kept in the device layer, so it never leaves the phone with a backup, an export or a handover. Without the network the screen says so and offers a retry.

- **The dashboard's pages** (`apps/dashboard`, answers 809 and 855), in the dashboard app alone, never in the teacher's. The Ministry's reference page asks whether its edit code is set (`GET /directory/reference/claimed`), sets it the first time (`POST /directory/reference/code`), and then, with the code in `Authorization: Bearer`, reads the draft and the versions (`GET /directory/reference/state`), saves each change to the draft (`PUT /directory/reference/draft`), publishes it (`POST /directory/reference/publish`) and publishes an old version again (`POST /directory/reference/republish`). A school's page reads the published list (`GET /directory/reference`), then asks and sets the school's own code the same way (`/directory/schools/<ID>/claimed` and `/code`), reads and saves the school's book (`GET` and `PUT /directory/schools/<ID>/book`), and renews a teacher's joining code (`POST /directory/schools/<ID>/teachers/<teacher>/code`). What is saved is what the page's user enters: schools, levels and options, or classes, pupils' names, registration numbers and sex, teachers' names and options, and the week, all made up. The edit code is held in the page's memory only, and forgotten by «قفل الآن» or when the tab closes; the dashboard keeps nothing in the browser but its language.

The server holds the list and the schools' books in the clear, outside any world, so the 7-day sweep never erases them; a school's book opens only to that school's edit code, kept as its hash, and a phone receives a school's data only for the joining code the school gave that teacher, and then only that teacher's classes and sessions. The server calls no one to keep it, and keeps no address beyond its rate limits' counts ([the server's README](apps/server/README.md#the-directory)).

Like any request to this server, these pass through Cloudflare and a Worker of the project's ([What the server sees](#demo-worlds)). A later page adds what it sends here in the pull request that adds it.

## Local source-PDF input

The curator's PC editor (#613) opens a PDF only through the browser's local file picker. PDF.js 6.5.438 is bundled with a dedicated local worker; neither PDF bytes, its name, its metadata nor page images are uploaded or put into a release. The original stays in memory until closed, replaced or the draft is left. Rendered PNGs and unverified plain-text row suggestions are for comparison with the form. No embedded PDF script, action, annotation link or viewer HTML is run. Scanned pages can be keyed manually; no OCR or AI service is called.

PDF viewing loads this build's own engine, worker, CMaps, fonts and JavaScript image decoders for JPEG 2000, JBIG2 and CCITT. Only a curator who opens a source PDF fetches them, as GET requests to the app's own host that carry no cookie, identifier or part of the PDF, so this step needs the network. The offline worker doesn't keep them, so a teacher's PC doesn't download them. It checks each file against the SHA-256 the installed build lists and refuses any other, so the app stays the build that was installed; a curator whose build the host has moved past installs the update first, if the engine's files changed. The earlier worker stays until the browser swaps it, once every tab of the app has closed. An update accepted before then still downloads the engine and keeps it, and a PDF worker it serves has no security policy of its own. After the swap that copy goes unused until the next update. The CMap and font bridge refuses paths, queries and addresses supplied by a PDF. The worker imports the decoders from a fixed path in the same build. Its own response carries the host's security policy, which refuses eval and scripts from any other origin, and its general-purpose network and browser-storage APIs are removed before the engine loads, from the prototypes behind its global too. Android has no PDF.js dependency.

Accepted complete draft edits use #612's existing signed, sealed national-space stream and the world's checked day. Opening the editor makes the same date/history reads. The source reference and item page are entered by the curator, not taken from local file names or metadata. A read error or stale revision cannot overwrite a draft; no teacher journal, pupil record or private note enters this flow.

## Offline calendar input

Only after the teacher selects Open file does Android's document picker select one local document (`EXTRA_LOCAL_ONLY`). The app reads that content URI with a byte limit and timeout, takes no persistent URI grant, and asks for no storage permission. It does not fetch URLs found in a file or QR code.

Only after the teacher selects Scan QR code does an unexported app screen request camera permission and decode frames locally with ZXing Core 3.5.4. Frames remain in memory, are cleared after decoding and are not saved or sent. Leaving or backgrounding that screen closes the camera. Refusing access leaves file input available. No Google Play service, online decoder, identifier, upload, analytics or new network permission is involved. The founder approved this dependency and scan-only camera access for #222 (answer 288 in the project's decision record). Reader mode (#246) and the new phone's restore (#247) use the same scan, for a progress statement's QR code and a direct transfer's one-time code, and add no permission or library.

Signed calendar updates (#223) come in through the same Open file and Scan QR code steps, and signed plan packs through Open file alone, up to 1 MB. The phone checks the signature itself, with Android's own platform crypto (ECDSA P-256), against the public keys bundled in the app's `data/dz/keys.json`; no key server, certificate list or revocation service is asked, and no new library or permission is involved (answers 303 and 316). Only an update or a pack the teacher applies is kept, in the local history; nothing is sent.

## Statements, exports, backups and transfers

None of these makes a network call. Each leaves the phone or comes in only when the teacher chooses, through Android's own document picker (`ACTION_CREATE_DOCUMENT` or `ACTION_OPEN_DOCUMENT`), print service or share sheet (`ACTION_SEND`). The teacher picks where it goes or what comes in, and the app makes no request.

- **Progress statements** (#245) print, save as a PDF, show as a QR code on the screen, or leave as a signed file through the share sheet. They carry no pupil data.
- **The full export** (#248) and **backups** (#247) are saved through the document picker. The export is under a password by default, and a backup is encrypted under the teacher's recovery key.
- **A direct transfer** (#247) sends one encrypted file through the share sheet, as Quick Share or Bluetooth, or saves it through the document picker. Its one-time code shows on the old phone's screen and is scanned or typed on the new one; it is kept nowhere. How Quick Share or Bluetooth carries the file is under Android's own settings.
- **The recovery sheet** (#247), which holds the recovery key, prints through Android's print service, to the printer the teacher picks. The app sends the key nowhere else.
- **Reader mode** (#246) opens a statement from a file the teacher picks (`ACTION_OPEN_DOCUMENT`, `EXTRA_LOCAL_ONLY`) or from its QR code, and keeps it in the local history. Its spot-check sheet and the subject council's merge print or save as a PDF through the print service or the document picker, and nothing about them is kept. Nothing is sent.
- **The restore** (#247) opens a backup, an export or a transfer file, and the marks check (#242) a CSV file, that the teacher picks from the phone, an SD card or a USB key (`ACTION_OPEN_DOCUMENT`, `EXTRA_LOCAL_ONLY`; #477, answer 495). The pickers show no cloud provider, so a file kept in a cloud folder must first be copied to the phone by the teacher.

## Notifications

The weekly digest and the daily preview (#234), and the backup reminder (#247), are notifications Android shows at times the app sets while it is open, with words it sets then. Android 13 and later ask the teacher for the notification permission once. No push service, server, Firebase or Google Play service is involved: nothing arrives from outside the phone and nothing is sent. A notification never shows a pupil's name or a mark, and when the phone hides sensitive content on the lock screen, only its title shows there. After a restart, the app sets the alarms still to come again, which needs Android's boot permission and no network (answer 406 in the project's decision record).

## Optional pack source links

A plan pack may name the address where its source file was found. Pack details show that address as text; reading them makes no request and launches nothing. Only when the teacher selects Open the source on an item, and confirms a notice that names the address's host, does Android hand the address to the user's browser, with the item's source page after `#page=`. The address opens only if it is a plain `https` address on a named host, in printable ASCII, with no user name, password or fragment of its own; any other address is shown and never opened. No record, identifier or query parameter is added. The browser may then contact that host under its own settings; this is not an in-app fetch or an embedded web view. Cancelling makes no hand-off (#225, answer 289).

## Plan-error reports

A teacher may report an error in a plan item. The report screen shows the exact text before it leaves: the pack and item IDs, the release, the kind of error, the teacher's note and, only if the teacher turns on credit and types it, a name. No class, school, pupil, record or device identifier is added, the teacher card's name is never filled in, and the screen asks the teacher not to write pupils' names in the note. Bidi control characters are removed from what the teacher types. Only when the teacher selects Share the report does Android's share sheet open with that text; the teacher picks the app, and the screen suggests `contact@djazair.dev`. The app makes no request and needs no network permission; whatever the chosen app does with the text is under its own settings (#225, answers 287 and 290).

## Problem reports

A teacher may report a problem from Help. The report screen shows the exact text before it leaves: what happened, in the teacher's words, the part of the app they chose, the app's version, Android's version and the route names of the last ten screens opened since the app started, kept in memory only, never their content or parameters. Every pupil's name the app holds, Arabic or Latin, whole or in part, is replaced with «تلميذ 1», «تلميذ 2» in what the teacher types before it is shown, as the class lists write it, with common spelling variants and attached prefixes; a name spelled another way may remain, which is why the teacher reads the whole report before sharing it. Registration numbers are replaced too, and bidi control characters are removed. No class, school, record or device identifier is added. Only when the teacher selects Share the report does Android's share sheet open with that text; the teacher picks the app, and the screen suggests `contact@djazair.dev`. Sharing keeps no copy, makes no request and needs no network permission (#249, answer 483).

While a demo world is open, the report screen also offers to send the report to the world's operators (#619, answer 657). Only when the teacher presses that button does the world's client send `POST /worlds/<world ID>/problems` to the demo server, with the world's pass and exactly three fields: the part of the app, the note as the preview shows it (pupils' names replaced, bidi controls taken out, line ends made new lines, other control characters spaces and lone surrogates replaced), and the app's version. Android's version, the last screens and anything else stay on the device, and the app adds nothing that names the teacher. The server answers the report's ID and a token; the token stays in the screen's memory, so the teacher can delete the report with `POST /worlds/<world ID>/problems/<report ID>/delete` while the screen is open, and is lost when it closes. The server keeps the report, with the day it came, until an operator marks it fixed, 12 months at most, and erases it with the world on its 7th day. If an answer is lost on the way, the report may be kept without the teacher's knowing its ID, and sending again keeps a second one; both end the same way.

## Crash reports

Crash reports are off until the teacher turns them on in Help. While they are on, a crash that stops the app keeps one file in the app's own folder, outside the history: the error's type, the places in the code its stack names (a function's name and its line and column, or its name alone in Hermes's own code, or a class, method and line, never a file path), the route names of the last ten screens opened, the app's version and Android's version. The error's message is never kept, since it may hold data; if a JavaScript stack's message cannot be set aside, no place in the code is kept. At the next start the teacher sees the report exactly as it would be shared, and chooses «إرسال», which opens Android's share sheet with that text, or «عدم الإرسال». Either way the file is deleted. Turning the switch off deletes a kept report, and nothing is kept while it is off. The app makes no request, Android's backup takes nothing, and erasing the phone's data deletes the file and the switch (#249, answer 483).

## Optional source link in Help

The source link is the fixed public address [github.com/djazairdev/minhajna](https://github.com/djazairdev/minhajna). Reading Help or a licence makes no request and does not launch another app. Only after the teacher selects the link and confirms a notice in their interface language does Android hand that address to the user's browser. No record, identifier, query parameter or other payload is attached. The browser may then contact GitHub under its own settings, revealing its normal connection/browser information to that site; this is not an in-app fetch or an embedded web view. Cancelling makes no hand-off. An unavailable browser does not prevent offline reading.
