# Network calls

Every network call that Minhajna's code makes is listed here, with the address, what is sent and why ([engineering rules](docs/contributing/engineering.md#pupil-data-and-privacy), [PRD §1.5](docs/prd/PRD.md#15-pupil-data-and-privacy-rules)). Adding or widening a call is a privacy-sensitive change, and this file changes in the same pull request.

| Part | Address | What is sent | Why |
|---|---|---|---|
| The shared core (`packages/core`) | None | Nothing | The core makes no network calls |
| Android app (`apps/android`) | The demo server, `https://minhajna-demo.djazair.dev` (answer 554), and only while a demo world is open (#559); outside a world, none. The app asks for the network permission for this alone (answer 570) | Inside a world only: the world's ID, its pass in `X-World-Pass`, and what the world's own flows send, all made up, and a problem report only when the teacher sends one to the world's operators (see [Demo worlds](#demo-worlds)) | Run the 0.7.0 demo. Nothing of the teacher's own records is sent. Help reads licence notices from the installed APK |
| PC web app (`apps/web`, #250) | Its own origin only: `https://minhajna.djazair.dev`, which the project serves through Cloudflare (answers 528, 531 and 537), or `http://127.0.0.1:4180` when tried locally. Cloudflare sees the visitor's IP address and browser at each visit, under its own policy; the project keeps no access logs. The host never sees what the teacher records ([the host guide](docs/contributing/web-host.md)) | GET requests for its own files: the page, the install script, the bundle, fonts, images, manifest, licences and `build.json`. Until the offline worker has installed them, each visit fetches them; from then on the worker answers from its cache. A newer build's files are fetched only once the teacher accepts its update. Help's source link opens the code's page only after the teacher confirms, as on the phone. Files are opened through the browser's file dialog and leave only as a download or through the computer's share menu, each chosen by the teacher; none is uploaded | Install the app and open it offline. Nothing the teacher types or records is sent, but a problem report the teacher sends to a demo world's operators ([Problem reports](#problem-reports)). The page's security policy allows one other address, and only to connect to: the demo server, `https://minhajna-demo.djazair.dev` (answer 554), which only a demo world's client calls, while a world is open (#559, [Demo worlds](#demo-worlds)). No script, font, tracker or service elsewhere can be reached, and the host check fails if the policy names any other address |

No result, history entry, passphrase, key or other user input is uploaded. There are no external scripts, telemetry or third-party endpoints |

The tests make no network calls either ([engineering rules](docs/contributing/engineering.md#tests)).

## Demo worlds

A demo world (0.7.0, choice D8) is the only part of the app that connects, on the phone and on a PC, and only to the demo server, `https://minhajna-demo.djazair.dev`, which the project runs ([the server's README](apps/server/README.md)). Answer 570 sets the rules:

- **A guard on the app's connections.** The app's first import wraps the global `fetch`, `XMLHttpRequest` and `WebSocket`, and on a PC `EventSource` and `navigator.sendBeacon` too (`apps/android/src/network/guard.ts`). Each refuses any address but the demo server, and the demo server too unless a world is open. On a PC, the page's own files stay open, and its security policy allows no other address; Android's debug builds keep Metro on the developer's computer. The globals do not cover React Native's native image loading, its networking and socket modules imported directly, or a native module's own requests, so the app uses none of them: a test reads the code and fails if it finds a remote image, such a module, an HTTP or socket call in the app's Kotlin, or a WebView that does not block network loads.
- **One client.** Only the world's client (`apps/android/src/network/world-network.ts`) sends to the demo server: to start the open world, or to that world's own paths. Each request carries the world's ID and its pass, which the device works out from the world's code; the code's secret never leaves the device. No cookie, cache or referrer goes with it, and it stops after 20 seconds. In a browser a redirect fails it; on Android, React Native follows a redirect itself, with the pass; the demo server sends none. An answer longer than 1 MiB, or one that comes after the world was left, is dropped.
- **Which pages may call it.** In a browser, the demo server answers only the PC web app's own origin, `https://minhajna.djazair.dev`, or `http://127.0.0.1:4180` and `http://127.0.0.1:8787` when it is tried locally, for the methods and headers the world's client sends, and never with cookies or other credentials (answer 583). A page elsewhere cannot read its answers.
- **What a world sends.** Its keys, sealed under its code, with its date; each space's sealed batches of exactly one size; and requests to certify a signing key the device made for that world. All of it is made up: a world never holds the teacher's own records, which stay shut while it is open (#558). In a teachers' world, its starter opens the world's observatory as the world starts (`POST /worlds/<ID>/insights`), holding made-up sendings from classes that do not exist, in as many requests as they take, or one request holding none when the start has no reference data. Once its teacher turns on the anonymous insights (#622, answer 697), and while the world is open, each term's end sends one sending for each class that follows a plan pack (`PUT /worlds/<ID>/insights/sendings`), the same text the world's insights page shows for that term: its format, a random ID for the class and term, the term's random token, the school and term's code, which the server, on receipt, replaces with a mark to count schools, the school year and term, the wilaya, grade and subject, the pack and release, the sessions on each item, the items merged, skipped, split or re-taught, and how far the class got. It holds nothing that identifies a teacher, a pupil or a session, and no date or reason. The world's store keeps each sending as sent. The server erases each world on its 7th day. One call carries the teacher's own words: a problem report, only when the teacher presses to send it to the world's operators ([Problem reports](#problem-reports)). A later call is added here in the pull request that adds it.
- **The pack editor's lifecycle (#612).** The curator and Ministry demo flows use the world's keys already held in memory, check `GET /worlds/:world/date`, read the national space, and put signed source-pack drafts and lifecycle changes on an opaque stream there, through the same `PUT /worlds/:world/spaces/national` and `POST`/`GET` batches calls. Every uploaded batch is 4,124 bytes; one whole change fits at most 128 batches and is refused before upload if it is larger. Pack IDs, source text, roles and stages stay inside the ciphertext. No teacher record, pupil data, code secret or unsealed key is sent. The device checks the world and signatures, and a damaged or incomplete authoring history blocks another write. A demo Ministry publication is marked Official only inside its world: real mode and another world refuse its file. This uses the existing demo flow chosen by the maintainer; it adds no publisher account or new address.
- **What the server sees.** It reads the device's IP address only to count its rate limits, in memory, and never logs or stores it; requests are never logged. In front of it, Cloudflare sees each request's IP address and browser, under its own policy, as for the PC app (#545).
- **What the observatory reads.** In a teachers' world, the observatory's Reports page on a PC (#627, answer 680) reads a term's figures only once the world's date has reached that term's end: first the packs they cover (`GET /worlds/<ID>/insights/figures?year=&term=`, with the school year and term), then one pack's figures at a time (the same with `&at=`, the pack's place among them). The figures come back already added up, the nation's and each wilaya's, every figure under its floor hidden by the server. The device that started the world, holding its starter token, ends that term's collection when the page finds it still open or still being formed (`POST /worlds/<ID>/insights/closed`, with the starter token and only the school year and term); ending it again changes nothing. Nothing else is sent.

## Offline calendar input

Only after the teacher selects Open file does Android's document picker select one local document (`EXTRA_LOCAL_ONLY`). The app reads that content URI with a byte limit and timeout, takes no persistent URI grant, and asks for no storage permission. It does not fetch URLs found in a file or QR code.

Only after the teacher selects Scan QR code does an unexported app screen request camera permission and decode frames locally with ZXing Core 3.5.4. Frames remain in memory, are cleared after decoding and are not saved or sent. Leaving or backgrounding that screen closes the camera. Refusing access leaves file input available. No Google Play service, online decoder, identifier, upload, analytics or new network permission is involved. The founder approved this dependency and scan-only camera access for #222 (answer 288 in the project's decision record). Reader mode (#246) and the new phone's restore (#247) use the same scan, for a progress statement's QR code and a direct transfer's one-time code, and add no permission or library.

Signed calendar updates (#223) come in through the same Open file and Scan QR code steps, and signed plan packs through Open file alone, up to 1 MB. The phone checks the signature itself, with Android's own platform crypto (ECDSA P-256), against the public keys bundled in the app's `data/dz/keys.json`; no key server, certificate list or revocation service is asked, and no new library or permission is involved (answers 303 and 316). Only an update or a pack the teacher applies is kept, in the local history; nothing is sent.

## Statements, exports, backups and transfers

None of these makes a network call. Each leaves the phone or comes in only when the teacher chooses, through Android's own document picker (`ACTION_CREATE_DOCUMENT` or `ACTION_OPEN_DOCUMENT`), print service or share sheet (`ACTION_SEND`). The teacher picks where it goes or what comes in, and the app makes no request.

- **Progress statements** (#245) print, save as a PDF, show as a QR code on the screen, or leave as a signed file through the share sheet. They carry no pupil data.
- **The full export** (#248) and **backups** (#247) are saved through the document picker. The export is under a password by default, and a backup is encrypted under the teacher's recovery key.
- **A direct transfer** (#247) sends one encrypted file through the share sheet, as Quick Share or Bluetooth, or saves it through the document picker. Its one-time code shows on the old phone's screen and is scanned or typed on the new one; it is kept nowhere. How Quick Share or Bluetooth carries the file is under Android's own settings.
- **The recovery sheet** (#247), which holds the recovery key, prints through Android's print service, to the printer the teacher picks. The app sends the key nowhere else.
- **Reader mode** (#246) opens a statement from a file the teacher picks (`ACTION_OPEN_DOCUMENT`, `EXTRA_LOCAL_ONLY`) or from its QR code, and keeps it in the local history. Its spot-check sheet and the subject council's merge print or save as a PDF through the print service or the document picker, and nothing about them is kept. Nothing is sent.
- **The restore** (#247) opens a backup, an export or a transfer file, and the marks check (#242) a CSV file, that the teacher picks from the phone, an SD card or a USB key (`ACTION_OPEN_DOCUMENT`, `EXTRA_LOCAL_ONLY`; #477, answer 495). The pickers show no cloud provider, so a file kept in a cloud folder must first be copied to the phone by the teacher.

## Notifications

The weekly digest and the daily preview (#234), and the backup reminder (#247), are notifications Android shows at times the app sets while it is open, with words it sets then. Android 13 and later ask the teacher for the notification permission once. No push service, server, Firebase or Google Play service is involved: nothing arrives from outside the phone and nothing is sent. A notification never shows a pupil's name or a mark, and when the phone hides sensitive content on the lock screen, only its title shows there. After a restart, the app sets the alarms still to come again, which needs Android's boot permission and no network (answer 406 in the project's decision record).

## Optional pack source links

A plan pack may name the address where its source file was found. Pack details show that address as text; reading them makes no request and launches nothing. Only when the teacher selects Open the source on an item, and confirms a notice that names the address's host, does Android hand the address to the user's browser, with the item's source page after `#page=`. The address opens only if it is a plain `https` address on a named host, in printable ASCII, with no user name, password or fragment of its own; any other address is shown and never opened. No record, identifier or query parameter is added. The browser may then contact that host under its own settings; this is not an in-app fetch or an embedded web view. Cancelling makes no hand-off (#225, answer 289).

## Plan-error reports

A teacher may report an error in a plan item. The report screen shows the exact text before it leaves: the pack and item IDs, the release, the kind of error, the teacher's note and, only if the teacher turns on credit and types it, a name. No class, school, pupil, record or device identifier is added, the teacher card's name is never filled in, and the screen asks the teacher not to write pupils' names in the note. Bidi control characters are removed from what the teacher types. Only when the teacher selects Share the report does Android's share sheet open with that text; the teacher picks the app, and the screen suggests `contact@djazair.dev`. The app makes no request and needs no network permission; whatever the chosen app does with the text is under its own settings (#225, answers 287 and 290).

## Problem reports

A teacher may report a problem from Help. The report screen shows the exact text before it leaves: what happened, in the teacher's words, the part of the app they chose, the app's version, Android's version and the route names of the last ten screens opened since the app started, kept in memory only, never their content or parameters. Every pupil's name the app holds, Arabic or Latin, whole or in part, is replaced with «تلميذ 1», «تلميذ 2» in what the teacher types before it is shown, as the class lists write it, with common spelling variants and attached prefixes; a name spelled another way may remain, which is why the teacher reads the whole report before sharing it. Registration numbers are replaced too, and bidi control characters are removed. No class, school, record or device identifier is added. Only when the teacher selects Share the report does Android's share sheet open with that text; the teacher picks the app, and the screen suggests `contact@djazair.dev`. Sharing keeps no copy, makes no request and needs no network permission (#249, answer 483).

While a demo world is open, the report screen also offers to send the report to the world's operators (#619, answer 657). Only when the teacher presses that button does the world's client send `POST /worlds/<world ID>/problems` to the demo server, with the world's pass and exactly three fields: the part of the app, the note as the preview shows it (pupils' names replaced, bidi controls taken out, line ends made new lines, other control characters spaces and lone surrogates replaced), and the app's version. Android's version, the last screens and anything else stay on the device, and the app adds nothing that names the teacher. The server answers the report's ID and a token; the token stays in the screen's memory, so the teacher can delete the report with `POST /worlds/<world ID>/problems/<report ID>/delete` while the screen is open, and is lost when it closes. The server keeps the report, with the day it came, until an operator marks it fixed, 12 months at most, and erases it with the world on its 7th day. If an answer is lost on the way, the report may be kept without the teacher's knowing its ID, and sending again keeps a second one; both end the same way.

## Crash reports

Crash reports are off until the teacher turns them on in Help. While they are on, a crash that stops the app keeps one file in the app's own folder, outside the history: the error's type, the places in the code its stack names (a function's name and its line and column, or its name alone in Hermes's own code, or a class, method and line, never a file path), the route names of the last ten screens opened, the app's version and Android's version. The error's message is never kept, since it may hold data; if a JavaScript stack's message cannot be set aside, no place in the code is kept. At the next start the teacher sees the report exactly as it would be shared, and chooses «إرسال», which opens Android's share sheet with that text, or «عدم الإرسال». Either way the file is deleted. Turning the switch off deletes a kept report, and nothing is kept while it is off. The app makes no request, Android's backup takes nothing, and erasing the phone's data deletes the file and the switch (#249, answer 483).

## Optional source link in Help

The source link is the fixed public address [github.com/djazairdev/minhajna](https://github.com/djazairdev/minhajna). Reading Help or a licence makes no request and does not launch another app. Only after the teacher selects the link and confirms a notice in their interface language does Android hand that address to the user's browser. No record, identifier, query parameter or other payload is attached. The browser may then contact GitHub under its own settings, revealing its normal connection/browser information to that site; this is not an in-app fetch or an embedded web view. Cancelling makes no hand-off. An unavailable browser does not prevent offline reading.
