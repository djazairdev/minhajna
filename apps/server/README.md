# Minhajna's server

The server package ([PRD §5.2](../../docs/prd/PRD.md#52-architecture)): one package, installed by whoever runs it. In 0.7.0 it is **the demo server** ([#516](https://github.com/djazairdev/minhajna/issues/516)): it holds made-up demo worlds in which every role, from the Ministry to the teacher, runs the national flow. It never holds real data, and it never holds a key to a school's or a teacher's records.

**Status:** the health check ([#538](https://github.com/djazairdev/minhajna/issues/538)), the worlds API ([#540](https://github.com/djazairdev/minhajna/issues/540)), the encrypted relay ([#541](https://github.com/djazairdev/minhajna/issues/541)) and the stand-in CA ([#554](https://github.com/djazairdev/minhajna/issues/554)), kept in PostgreSQL and erased on their 7th day ([#542](https://github.com/djazairdev/minhajna/issues/542)), the operators' view of the server ([#618](https://github.com/djazairdev/minhajna/issues/618)), the admin log, problem reports and security logs ([#619](https://github.com/djazairdev/minhajna/issues/619)), and the backups' restore tests ([#620](https://github.com/djazairdev/minhajna/issues/620)).

## The worlds API

A world is named by the first five characters of its code; the rest of the code never reaches the server. The device derives the world's pass from the code's secret and sends it in `X-World-Pass`; the server keeps only its hash, and answers a wrong pass exactly as an unknown id.

| Request                                                                         | Does                                                                                                              | Answers                                                                                                                                                                        |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `POST /worlds` with `{world, sealed, date, announcedDays, pass}`                | Starts a world: its id, the sealed world in base64url (at most 48 KB), its date, the announced days and its pass  | `201 {starter}`, the starter token, given once; `409` if the id is taken                                                                                                       |
| `GET /worlds/:world`, with the pass                                             | Joins a world                                                                                                     | `{sealed, date, announcedDays}`                                                                                                                                                |
| `GET /worlds/:world/date`, with the pass                                        | Reads the world's date and announced days                                                                         | `{date, announcedDays}`                                                                                                                                                        |
| `POST /worlds/:world/date`, with the pass and `Authorization: Bearer <starter>` | Moves the date to the next announced day                                                                          | `{date}`; `403` without the starter token; `409` when no day is left, or when the date or the announced days changed meanwhile                                                 |
| `PUT /worlds/:world/announced-days` with `{announcedDays}`, with the pass       | Replaces the announced days after the world's date with those a published calendar gives, keeping the days before | `{announcedDays}`; `400` for a day on or before the date, more than 400 days in all or another field; `404` without the world or its pass; `409` when the date moved meanwhile |

- **Probing:** a wrong pass answers exactly as an unknown id, and takes as long. Only a start can tell that an id is taken (`409`), and starts are the most limited requests.
- **The starter token** is kept only as its SHA-256 hash, so the store alone cannot move a date. No answer may be cached (`Cache-Control: no-store`).
- **Rate limits:** each address may start 5 worlds an hour, make 60 other world requests and 1,200 relay requests (the relay's count also takes what a device reads as it goes: `GET /worlds/:world/ca`, `GET /worlds/:world/date`, and the stand-in's `GET /worlds/:world/state/receiver` and `GET /worlds/:world/state/deliveries`) in 10 minutes, and store 20,000 batches a day (about 82 MB), a share or a sending counting as the batches its bytes would fill, and an opening's sendings as the batches their bytes together would fill, plus one for each school's mark new to the world, and keep 60 insights sendings a day, with totals for everyone (140,000 batches a day, so a week of them fits the server's cap: about 11 seeded worlds a day whose every school's term is filled, answer 626; 20,000 sendings a day). Only batches stored and sendings kept count: a refused upload costs nothing. An IPv6 address counts by its /64. Addresses stay in memory until the first request after their window, up to a day for uploads and sendings, and are never logged or stored. `TRUST_PROXY=cloudflare` reads the address from Cloudflare's header.

## The pack desk

A world's pack-editor accounts, and each pack release's steps (#612, R-4.3-09, R-6.7-02). Every request carries the world's pass. An account's token, like the starter token, is kept only as its SHA-256 hash, and no answer may be cached.

| Request | Does | Answers |
| --- | --- | --- |
| `POST /worlds/:world/packs/accounts` with `{role}`, and `Authorization: Bearer <starter>` | Makes the world's `curator` or `ministry` account, replacing any before it | `201 {role, token}`, the token given once; `403` without the starter token |
| `GET /worlds/:world/packs/account`, with `Authorization: Bearer <account>` | Signs in | `{role}`; `403` for any other token |
| `POST /worlds/:world/packs/steps` with `{id, release, expected, stage, status, digest, by, day, previous, successor}`, with `Authorization: Bearer <account>` | Takes a step of a release: draft, under review, published, then superseded or withdrawn | `201`, the step with its revision, role and the signature of the world's stand-in CA over `minhajna/pack-step/1`; `403` when the account may not; `409 {problem}`, `date` when the world's date moved and `revision` when the signed step it shows doesn't hold |
| `GET /worlds/:world/packs/steps` | Reads each release's latest step | `{steps}` |

- **Roles:** an account moves only what it holds, but the Ministry's may publish what a curator has under review, and what it publishes is Official. No curator's step ever is.
- **What it sees:** a release's name, stage and status, and a digest keyed with the world's sealing key, never the release itself, which stays sealed on the world's national space. A step names no person.
- **Two at once:** a device shows the step it read, signed, so the server holds no release's state to judge by. The sealed stream takes one record a revision and decides which of two steps counts, and one left unused holds nothing back. `GET .../steps` is a log of what was taken, so its latest step may be one the stream never took.

## The encrypted relay

Inside a world, with its pass, clients exchange sealed records through spaces: one per school and per directorate, whose ids the clients draw, and the one national space, named `national` (PRD §5.8).

| Request                                                                             | Does                                                                                                                                                                                               | Answers                                                                                                          |
| ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `PUT /worlds/:world/spaces/:space` with `{kind}`                                    | Opens a space of kind `school`, `directorate` or `national`                                                                                                                                        | `{kind}`; `409` if it exists with another kind, or the world holds 2,000 spaces                                  |
| `POST /worlds/:world/spaces/:space/batches` with `{stream, first, batches}`         | Adds a stream's next 1 to 128 sealed batches, all or none; a stream is numbered from 0 with no gap                                                                                                 | `201 {added}`; `409` naming the stream's next number when `first` is not it                                      |
| `GET /worlds/:world/spaces/:space/batches?after=n`                                  | Reads up to 128 batches after arrival number `n`                                                                                                                                                   | `{batches: [{seq, stream, number, bytes}], more}`                                                                |
| `POST /worlds/:world/seed/batches` with `{spaces, streams}`, with the starter token | Seeds a world, a national one for #548: opens up to 128 spaces `{space, kind}`, then adds up to 128 batches in all to streams `{space, stream, first, batches}`, in order, each stream all or none | `201 {opened, added}`; `403` without the starter token; `400`, `409` or `507` naming the space or stream refused |

- **Seeding:** only the device that started a world, with its starter token, seeds it (the server cannot tell a world's kind, so any world may be seeded), in about a dozen requests for 68 schools and 462 teachers (answers 625 and 626). A seeding counts once against the relay's limit and by batch against the daily quota; a refusal stops it there and keeps what came before, so a start that fails is started again, and the half-seeded world is erased on its 7th day, since nobody holds its code.
- **One size:** every batch is exactly 4,124 bytes: the core's 4,096-byte batch sealed with AES-256-GCM. Anything else is refused, so a batch's size says nothing.
- **The minimum:** the server keeps each space's id and kind, and each batch's stream, number, arrival order and sealed bytes. No names, no times, no addresses.
- **Caps:** a world holds at most 2,000 spaces and 16,384 batches (about 68 MB), room for every seeded school's term (answer 626). The server holds at most 1,000,000 batches in PostgreSQL (about 4 GB), or 50,000 in memory (about 206 MB), and answers `507` beyond; uploads to different worlds at the same moment may pass that cap by a few.

## The stand-in CA

Each world has its own stand-in certificate authority ([#554](https://github.com/djazairdev/minhajna/issues/554), answer 564), which certifies the keys teachers sign their weeks with. A teacher's signing key is made on the device and never leaves it, except a seeded teacher's, which the device that starts a world makes and uploads sealed under a key only the world's code gives (answer 625).

| Request                                                                           | Does                                                                                                                                      | Answers                                                                           |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `GET /worlds/:world/ca`, with the pass                                            | Reads the CA's public key, which devices check the world's certificates against                                                           | `{publicKey}`, its SPKI in base64                                                 |
| `POST /worlds/:world/certificates` with `{world, subject, publicKey, signature}`  | Certifies the P-256 key a request names, when the request is signed by it and names this world                                            | `201` with the certificate, marked as a stand-in's and issued on the world's date |
| `POST /worlds/:world/seed/certificates` with `{requests}`, with the starter token | Certifies up to 128 requests at once for a seeded world's teachers (#548), each read as above, counted once with the other world requests | `201 {certificates}`, in the requests' order; `403` without the starter token     |

- **What it proves:** a request proves only that the device holds its key. In the demo, anyone with a world's code acts in any role, and the server is the CA and hands out its key, so a demo signature proves nothing against the server. Every certificate says it is a stand-in's, and only the state's CA, outside Minhajna's server, can make a signature evidence (answers 563 and 564).
- **The key:** an ECDSA P-256 key, as the devices' own are (answer 580), made the first time the world needs it and kept with the world, so it is erased with it, and lingers only in the sealed archive's WAL and base backups for about two days, like every row (see "What the bucket keeps and shows"). It certifies nothing outside its world, and never changes within it, so a device fetches it once and keeps it. The certificate's texts are those of [`packages/core/src/certify.ts`](../../packages/core/src/certify.ts), and the tests check the server's certificates with the core's own checks.

## The totals above the school

- **A school's share:** `PUT /worlds/:world/totals/:day/shares`, with the pass, takes a share as [`packages/core/src/total-shares.ts`](../../packages/core/src/total-shares.ts) prepares it on a device that holds the school key, for one of the world's announced days that its date has reached: `201 {id}` when new, `200 {id}` when it replaced the share of the same ID; `422` for a day not announced or not reached yet; `400` for a share for another day or of any other shape; `413` over 256 KB, which a CEM's share over every pack of its grades fits; `409` beyond 2,000 shares a day, or beyond what a day's shares may hold: 64 directorates, 64 subjects, 20,000 plan items and 64 MB (answer 628), a name once taken counting while the server keeps the day. It counts under the relay's limits, and a share kept costs the daily quota of uploads as many batches as its bytes would fill sealed (`429` beyond it).
- **What a share holds:** its directorate and, by subject, counts only: what the school's assignments show and what its signed weeks add up to. It names no school, class or teacher, the server never shows one back, and every share of a world is erased with it. In the demo the server sees each share before adding them up; cryptographic secure aggregation comes later (choice D2).
- **The day's totals:** `GET /worlds/:world/totals/:day`, with the pass, answers the Ministry's view of the shares kept for an announced day the date has reached, every directorate's figures by subject and over every subject and the nation's, and with `?directorate=` one directorate's own: `422` for a day not announced or not reached yet, `400` for a directorate not named as the reference data names one. As anyone with the pass may ask for every view, the figures hidden are worked out over all of them together, through a copy of the core's floors: under the directorate floor (5 teachers and 3 schools), the nation's under its own, and any figure that would let a hidden one be worked out by subtraction; the Ministry's view hides, as well, a directorate under the wilaya floor (10 teachers and 3 schools). A directorate's own view lists the subjects it holds, the Ministry's every subject. Over every subject, a figure counts each school's teachers as its largest subject's, at least, since one teacher may teach several. Plan items show only by subject, each hidden when fewer than 3 schools did it, and another with it when it alone would be hidden. A hidden figure or item is `null`. The server keeps the names of the last 64 days, and the sums of the last days whose shares take 128 MB in all, worked out until a share comes in, in memory, as the demo runs one server, and forgets them with the world. The floors protect one answer: two announced days' answers may still differ by one school's figures, as when its first share comes in, a known limit.
- **No series:** only announced days are taken, so no weekly or monthly totals form (R-5.10-11).

## The operators' console

`GET /worlds/:world/admin/system`, with the pass, answers what the operators' console shows of the server ([#618](https://github.com/djazairdev/minhajna/issues/618), answer 655). In the demo the operator is a role like the others, so any world's pass opens it; named administrators with two-factor sign-in wait for a real deployment (choice D11). It counts with the other world requests.

| Field         | Holds                                                                                                                                                                                                                                             |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `version`     | The package's version                                                                                                                                                                                                                             |
| `fingerprint` | The SHA-256 of the server's built code, or `null` when it cannot be read                                                                                                                                                                          |
| `parts`       | The parts its code runs: `gateway`, `relay`, `totals`, `standins`, the state's stand-ins, and `observatory`                                                                                                                                       |
| `storage`     | `postgresql` or `memory`                                                                                                                                                                                                                          |
| `database`    | With PostgreSQL, `ok`, or `failing` when it refuses, answers oddly or takes more than 2 seconds                                                                                                                                                   |
| `archive`     | With PostgreSQL answering, `on` when it is set to archive its write-ahead log, which is what keeps the backups, or `off`                                                                                                                          |
| `archiving`   | With `archive` `on`, from PostgreSQL's own counters: `ok`, `failing` when the last failure is newer than the last file archived, or `waiting` when none has been archived ([#620](https://github.com/djazairdev/minhajna/issues/620), answer 658) |
| `restore`     | With `archive` `on`, the newest restore test in the admin log, `{day, result}` with `passed` or `failed`, or `null`                                                                                                                               |

- **No time:** `archiving` never says when a file was archived, since files are archived as worlds are written, and their times would say when the demo was used.
- **The same answer through every world:** it describes the server as a whole and names no world, space or person.
- **When the database fails:** if checking the pass takes more than 2 seconds or fails, the answer is `503` with `storage` `postgresql` and `database` `failing`, the same to everyone, so the console can still say so; it gives the version and the fingerprint to a caller without the pass then, which `/health` and the published release give anyway.
- **The fingerprint** covers the server's built code alone, every file under `dist/src`, not `node_modules`, `package.json` or the migrations. For each file, in the order of the paths' code units: its path from `dist/src`, with `/` between folders, a newline, the lowercase hex SHA-256 of its bytes, and a newline; the fingerprint is the lowercase hex SHA-256 of all of that. It is worked out as the server loads, so it describes the code it runs, and is `null` when that code holds anything but folders and plain files. A build of the same source gives the same one with the same `package-lock.json`, `tools/prisma/package-lock.json` (Prisma's version shapes the generated client), `tsconfig.base.json` and `prisma/schema.prisma`, so anyone can rebuild the published source and compare: `npm run build && npm run fingerprint`.

## The observatory

- **Only in a world whose starter opened it** (answer 676): the server cannot tell a world's kind, so a teachers' world's starting device opens its observatory, and every other world, a national one among them, whose classes are all in school spaces, refuses insights sendings (R-8.4-05).
- **Opening it:** `POST /worlds/:world/insights`, with the pass and the starter token, body `{ "sendings": [...] }` of up to 256 made-up sendings in at most 1 MB, opens the observatory and keeps them, for seeding a teachers' world; every sending is checked before any is kept. `200 {kept}`; `404` for no world or a wrong pass; `403` without the starter token; `400` for any other body; `413` over 1 MB; `409` when a sending's ID is another token's, beyond 4,096 sendings a world, or when its term's collection, or that of the sending it would replace, has ended, the sendings before it kept. It may be sent again to add more. It counts once under the relay's limits, and the sendings kept cost the daily quota of uploads as many batches as their bytes together would fill sealed, and one more for each school's mark new to the world (`429` beyond either).
- **A sending:** `PUT /worlds/:world/insights/sendings`, with the pass, takes one class's sending for a term as [`packages/core/src/insights.ts`](../../packages/core/src/insights.ts) builds it (answer 675): `201 {id}` when new, `200 {id}` when it replaced the sending of the same ID and token; `404` for no world or a wrong pass; `409` when the world holds no observatory, when the ID is another token's, beyond 4,096 sendings, or when its term's collection, or that of the sending it would replace, has ended; `400` for any other shape; `413` over 64 KB. It counts under the relay's limits; a sending kept counts against a daily limit of 60 sendings by address and 20,000 for everyone, and costs the daily quota of uploads as a share does (`429` beyond any of them); a refused one costs nothing.
- **What is kept:** each sending by its ID with its token, never its school-and-term code, which is dropped on receipt and never stored or logged; it names no school, class or teacher, holds no date but its year and term, is never shown back, and is erased with the world; with it, the terms whose collection ended and their figures, by pack, erased with the world too.
- **Counting schools** (answer 677): on receipt, the code becomes a hash under a key the process draws when it starts and never writes anywhere, and the hash its school's mark for the run: the run's own random prefix and a number in turn, kept with the sending in place of the code, never drawn twice in a run, and given back when the store refuses the sending, unless another sending took it meanwhile, never when the store fails, as it may have kept the sending. The hash stays in memory only, so a school's later sendings get the same mark, and is forgotten with the world. A mark names no school and cannot be worked back to its code. A restart draws a new prefix, so a figure counts its schools as the most distinct marks of any one run among its sendings: fewer than it holds at worst, never more. A sending sent again takes its new mark in place of its old. A school's code is a new one each term, so a figure counts schools within one year and term. A world holds at most 4,096 marks, and every world 1,048,576, past which a school is marked as not counted; the hash is held as its first 128 bits beside the mark's number, about 70 MB at the cap. A sweep forgets the marks of the worlds it erased, but those of a world started meanwhile under the same ID.
- **Ending a term** (answer 678): `POST /worlds/:world/insights/closed`, with the pass and the starter token, body `{ "year": "YYYY-YYYY", "term": 1 }` and nothing else, the year's two years in turn, ends the term's collection once for good, at most 12 terms a world, then forms its figures from the term's sendings, which stand still from then on: `200 {year, term}`, again as well, forming the figures if a first try failed; `404` for no world or a wrong pass; `403` without the starter token; `400` for any other body; `409` when the world holds no observatory or has ended 12 terms. From then on a sending for the term, or one replacing a sending of it, is refused with `409`. It counts under the relay's limits (`429` beyond them).
- **The figures** (answer 678): `GET /worlds/:world/insights/figures?year=YYYY-YYYY&term=1`, with the pass, answers an ended term's packs, `{year, term, packs}`, each by its `grade`, `subject`, `pack` and `release`, only those whose nation's figure is shown, and with `&at=N` the figures of the pack at that place, `{year, term, at, figures}`, as kept when the term ended, never worked out again, so no answer holds more than one pack's and reading them before and after one sending tells nothing of it; `409` while the collection is open or the figures are being formed, `400` for a year, term or place not given right, `404` for no world or a wrong pass, and it counts under the relay's limits. A pack's figures give the nation's figure and each shown wilaya's: `classes`, `teachers` (distinct tokens), `schools`, `reached` (`median`, `low` and `high`, the quartiles, in thousandths) and, for the same items in every figure, at most 512, each item's `classes`, the median of its `sessions` among the classes that logged any on it, a class at 0 counting only in the item's `classes` and shares (given only when the classes that logged some cover the floor) and the shares that `merged`, `skipped`, `split` or `retaught` it, each a band in percent (under 5, 5 to under 15, 15–30, 30–50, 50–70, 70–85, 85–95, 95 and over, neighbours merged for a small figure so a band holds two counts at least). A figure under 10 teachers or 3 schools, or one the nation's would reveal by subtraction, is hidden through the same floors as the totals, a wilaya left out and an item `null`. Each pack's figures give `setAside`, how many of its classes were set aside as outliers, beside a nation's figure shown, else `null`. The keys of a kept figure stay in the order formed.
- **Outliers** ([#628](https://github.com/djazairdev/minhajna/issues/628), answer 679): before a term's figures are formed, the sendings no real class would send are set aside, never refused or erased, and count toward no figure, floor or median: every sending of a token, one teacher's for one term, that names more than one wilaya or more than 24 courses in the term; then, in a pack and release still holding 20 sendings at least, a sending whose sessions over the term add up past the upper quartile by three times the distance between the quartiles, taken as twice the median at least and one session, so the fence stands some seven medians up or more and a made-up sending must stay under it to count. There is no lower fence, as a low total cannot be told from a class that began logging late; sendings that are most of a pack outweigh any fence.

## The operators' logs and problem reports

Kept apart, each by its own rule ([#619](https://github.com/djazairdev/minhajna/issues/619), answer 656), each request with a world's pass and counted with the other world requests.

| Request                                                                        | Does                                                                   | Answers                                                           |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------- | ----------------------------------------------------------------- |
| `GET /worlds/:world/admin/log`                                                 | Reads the admin log's newest 200 lines                                 | `{lines: [{day, action, detail}]}`, newest first                  |
| `GET /worlds/:world/admin/security`                                            | Reads the security log                                                 | `{keptDays, days: [{day, counts}]}`, newest first                 |
| `POST /worlds/:world/problems` with `{part, note, version}`                    | Sends a problem report, as the app shapes it                           | `201 {id, token}`; `409` beyond 200 a world                       |
| `GET /worlds/:world/problems`                                                  | Lists the world's reports                                              | `{problems: [{id, part, note, version, received}]}`, newest first |
| `POST /worlds/:world/problems/:id/fixed`                                       | Marks a report fixed, which erases it and adds a line to the admin log | `{id}`; `404` for no such report                                  |
| `POST /worlds/:world/problems/:id/delete` with `Authorization: Bearer <token>` | Its sender deletes it                                                  | `{id}`; `404` for no such report, or another token                |

- **The admin log** is the server's own, kept in PostgreSQL and so in the backups: one line per administrative action, by the UTC day it was taken, never a clock time, and no name, since the demo's operator is a role, not a named person (choice D11). The actions: `server.started`, with the version, the fingerprint (`none` when it has none) and any migrations applied as it started; `worlds.erased`, with how many a sweep erased; `problem.fixed`, with the report's ID, written in the same transaction as the report's erasure; and `restore.tested`, which the container writes itself after each restore test, with `result` `passed`, or `failed` and the `step` that failed (see "The container image"). It keeps 12 months, and the newest 1,000 lines of reports marked fixed apart from the newest 1,000 of every other action, so marking reports fixed never pushes the server's own lines out.
- **Problem reports** are a world's: the `part` of the app, as the app's own report names it (`today`, `classes`, `roll`, `marks`, `plan`, `documents`, `settings` or `other`), a `note` of 1 to 1,000 characters, some of them shown, with no control character but a new line, no lone surrogate and no bidi embedding, override or isolate, whose pupils' names the device has already replaced, and the app's `version`. Each is kept with the UTC day it came until it is marked fixed or deleted, 12 months at most, and is erased with its world; the token is given once and kept only as its SHA-256 hash.
- **Security logs** are kept apart from everything else: in memory only, never in the database or its backups, as counts by UTC day of requests over the rate limits (`rate-limited`), a world id and pass that opened nothing (`pass-refused`), a starter token refused (`starter-refused`), and certificate requests and deliveries to the stand-in refused (`certificate-refused`, `delivery-refused`). They hold no address, world, space or time, keep the last 7 days, and are lost when the server stops, so they can measure or judge nobody. A national deployment keeps them for the shortest time the law allows.

## Storage

With `DATABASE_URL`, worlds, spaces and batches, the stand-ins' keys and receipts, the schools' shares, observatories with their sendings ([#621](https://github.com/djazairdev/minhajna/issues/621)), ended terms and figures ([#626](https://github.com/djazairdev/minhajna/issues/626)), the admin log and the problem reports are kept in PostgreSQL ([#542](https://github.com/djazairdev/minhajna/issues/542), answer 550), so they outlive a restart; without it, in memory, and lost when the server stops. Their tables are described in [`prisma/schema.prisma`](prisma/schema.prisma), and the server queries them through the Prisma Client generated from it (Prisma 7, answer 551), which needs no download and no engine.

- **A world is erased on its 7th day** (answer 548), counting the day it started, in UTC: the server sweeps when it starts and every hour, so a server that stays up has a world gone within the hour its 7th day begins, its spaces and batches with it, and its observatory, ended terms and figures. On the demo host the container sleeps when idle, and its Worker wakes it each day, so there a world may wait for that day's sweep; a request wakes the same sweep, which ends before the server answers, unless the sweep itself fails, when the server tries again the next hour.
- **Uploads to one world take turns:** each locks its world's row, so a world's caps and its streams' numbers hold. One that waits more than 5 seconds for a connection or 8 for its turn, or takes more than 10 once started, is answered `503` with `Retry-After`, to be sent again.

- **Migrations are plain SQL,** in `prisma/migrations/<name>/migration.sql`, each generated with `prisma migrate diff --script` and reviewed before it is committed. CI applies them to an empty database and fails if they differ from the schema.
- **The server applies any missing migration when it starts with `DATABASE_URL`,** and `npm run migrate` does the same. Each is applied once, in order of name, in its own transaction, and recorded with its SHA-256 in `minhajna_meta.migration`; a migration whose file changed after it was applied is refused, as is a file that opens or closes its own transaction.
- **With `psql` alone,** on a machine with no Prisma tool and no internet, from this folder: it stops at the first failure, skips what is applied, and takes the same lock as the server.

  ```bash
  set -e
  psql "$DATABASE_URL" -c 'CREATE SCHEMA IF NOT EXISTS minhajna_meta' -c 'CREATE TABLE IF NOT EXISTS minhajna_meta.migration (name text PRIMARY KEY, sha256 char(64))'
  for dir in prisma/migrations/*/; do
    name=$(basename "$dir")
    [ -n "$(psql "$DATABASE_URL" -tAc "SELECT 1 FROM minhajna_meta.migration WHERE name = '$name'")" ] && continue
    psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -1 -c 'SELECT pg_advisory_xact_lock(7042542)' -f "${dir}migration.sql" -c "INSERT INTO minhajna_meta.migration (name) VALUES ('$name')"
  done
  ```

- **Prisma's command line** lives in `tools/prisma/` with its own lockfile, so it never installs with the server: `npm run tools` installs it, and `npm run build` runs its `generate`, which downloads nothing.
- **A new migration:** change `schema.prisma`; against a database with every committed migration applied, run `DATABASE_URL=… npm run diff -- --script`; commit its output as `prisma/migrations/<next number>_<name>/migration.sql`, with the licence header the others carry.

## The container image

The demo runs from one image ([#633](https://github.com/djazairdev/minhajna/issues/633), answer 550): the server and PostgreSQL 18 together, with [WAL-G](https://github.com/wal-g/wal-g) keeping the database in an S3-compatible bucket, R2 for the demo, so a container that starts on an empty disk finds every world as it was. Build it from the repository's root:

```bash
docker build -f apps/server/Dockerfile -t minhajna-server .
```

- **On an empty disk,** it restores the latest base backup and every archived WAL file from the bucket; when the bucket holds none, it makes a new database and backs it up at once. A restore lands in a separate folder first, so a failed one leaves nothing half-made. If the bucket cannot be read within `BUCKET_WAIT` seconds (120), or the backup restored within `RESTORE_WAIT` (1800), it stops rather than start an empty or partial database. A WAL file the bucket fails to give is asked for 5 times over about 30 seconds; then recovery stops, rather than open a database without it, and the next container tries again.
- **While it runs,** PostgreSQL archives each WAL file as it fills, and at least every `ARCHIVE_TIMEOUT` seconds (60), so a container lost without warning loses at most that much. A base backup is taken whenever the latest is `BACKUP_EVERY` seconds old (a day), on starting too, and the last two are kept.
- **After each daily base backup,** though not a new database's first, a restore is tested (`container/restore-test.sh`, answer 658): the latest base backup is fetched into a scratch folder beside the database, a second PostgreSQL with 16 MB of shared buffers recovers it from the archived WAL on a socket of its own, with no network, within `RESTORE_WAIT`, and the restored database must answer, hold no migration but the live one's, in their order up to what the archive has reached, and read its worlds' table. The folder is erased at the end, passed or failed, and on the next start if the container stops in the middle. The result goes to the admin log as `restore.tested`, by the UTC day. With less than twice the database's size, its write-ahead log aside, free on the disk it fails at the step `room`, fetching nothing, so a copy never fills what the live database writes to.
- **On `SIGTERM`,** the server stops, the last WAL file is archived, and PostgreSQL stops. That takes longer than the usual 10 seconds' grace: give the container at least 120 (`docker run --stop-timeout 120`, or the host's equivalent), or a stop may lose up to a minute of writes.
- **The bucket comes from the environment,** never from the image or the repository: `WALG_S3_PREFIX` (`s3://<bucket>/<path>`), `AWS_ENDPOINT` (R2's `https://<account>.r2.cloudflarestorage.com`), `AWS_REGION` (`auto` for R2), `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. Without `WALG_S3_PREFIX` it refuses to start, unless `ARCHIVE=off` says to keep nothing, for trying the image.
- **Seal the archive** with `WALG_LIBSODIUM_KEY` (32 random bytes, in hex with `WALG_LIBSODIUM_KEY_TRANSFORM=hex`), so whoever can read the bucket reads nothing: without it, world ids, hashes, erasure days, sealed batches and each world's stand-in CA key are in the clear there. Keep the key with the bucket's credentials; without it the archive cannot be restored.
- **What the bucket keeps and shows:** an erased world leaves the database at once, but stays in the bucket until the WAL and the base backups that hold it are replaced, about two days at most while backups run; deleted rows may also linger in later backups until PostgreSQL reuses their space. That holds for problem reports too, whose notes are free text, after they are fixed, deleted or erased with their world. The times the bucket stores with each WAL file and backup show when the demo was used, to the minute, to whoever reads the bucket.
- **Inside,** the start script runs as root only to start PostgreSQL as `postgres` and the server as `minhajna`, a database role that is no superuser, without the bucket's settings, and to make the restore test's folders. PostgreSQL listens on its socket only, the server on port 8080, and nothing in the image calls out but WAL-G, to the bucket. Cloudflare's container can close outbound addresses only by having the image trust a certificate of its own, which WAL-G would need too, so on the demo host they stay open ([docs/demo-host.md](../../docs/demo-host.md), answer 753); a national deployment closes them at its firewall. Its logs carry no clock times: they are cut from PostgreSQL's and WAL-G's lines.
- **Its notices:** `/srv/minhajna/NOTICES.txt` holds the licence and notices of every package the image holds and what it adds beside them (`tools/notices.ts`, `container/NOTICE.txt`), written as the image is built, so it can't fall behind the lockfile. `/srv/minhajna/licenses/` holds the full texts that file refers to.
- **Its test** (`test/image.test.ts`) builds the image and runs it against an S3 stand-in, [SeaweedFS](https://github.com/seaweedfs/seaweedfs) in `compose.yaml`'s `archive` profile, with a sealed archive. It stops a container after a world was written both before and after its latest base backup, and finds both in a new container on an empty disk. It also waits for the first container's restore test to pass and the operators' view to say so, and makes one fail at each of fetching, with the bucket out of reach, recovering, with a WAL file refused, and checking, with a migration the copy lacks, nothing of the copy left after any of them. Too little room is not tried. It needs Docker, so it runs only with `TEST_IMAGE=1`, as the Server image workflow does.

## Before deploying

- **Set `DATABASE_URL`,** or worlds are lost at every restart; the image sets it for its own PostgreSQL. A deployment outside the image carries `dist/`, `prisma/migrations/` and the server's `package.json`, lockfile and `.npmrc`, and installs with `npm ci --omit=dev`, which never brings Prisma's command line.
- **One container per bucket path:** two containers running on the same `WALG_S3_PREFIX`, as in a blue-green deploy, split the archive, and the next restore keeps only one of them. Stop the old container before the new one starts.
- **Give it a stop grace of 120 seconds** and a disk for the database and some days of WAL, mounted at `/var/lib/postgresql`, never at the database's own folder below it, where a restore could not move into place. If the bucket stays out of reach, WAL piles up until the disk is full, and PostgreSQL stops.
- **Behind Cloudflare,** set `TRUST_PROXY=cloudflare` and make sure the Worker in front passes `CF-Connecting-IP` on, as [`host/worker.ts`](host/worker.ts) does; otherwise every request has the Worker's address and the per-address limits become one shared limit.
- **The demo's own host** is [docs/demo-host.md](../../docs/demo-host.md) ([#545](https://github.com/djazairdev/minhajna/issues/545)): `host/` holds its Worker, its Wrangler settings and its host check. A deployment elsewhere needs none of them.

## The whole demo on this computer

From the repository's root, with Node.js 26.13 or later and Docker with Compose v2:

```bash
npm run demo
```

- **What it does:** it starts PostgreSQL ([`compose.yaml`](compose.yaml), on port 54320, this computer only), installs any part's locked dependencies that are missing or older than its lockfile, builds the server and the PC web app, and runs them: the server on <http://127.0.0.1:3000/health>, the web app on <http://127.0.0.1:4180/>.
- **Stopping:** Ctrl-C stops all three. The database keeps its made-up worlds for the next run; `npm run demo -- --fresh` clears them first.
- **Local only:** the database trusts every connection from this computer and has no password, so the compose file is never used for a deployment.
- **In the dev container** ([CONTRIBUTING.md](../../CONTRIBUTING.md#or-in-a-dev-container), #634), the container starts this PostgreSQL and the S3 stand-in itself, with no port on the computer, and names its database in `MINHAJNA_DEMO_DATABASE`. `npm run demo` then runs no Docker, leaves PostgreSQL running when it stops, and with `--fresh` empties the demo database instead of its volume.
- **Demo scenarios** ([`tools/demo-scenario/`](../../tools/demo-scenario/scenario.js), #629): with the demo running, `node tools/demo-scenario/run.js` starts a world, acts as its roles, moves its date and checks what each role sees, as their devices would. CI runs them against `npm run demo -- --fresh`. A scenario plays the same world each time, so run it on a fresh database; on one it has run on, it says so. `--server` names another server and `--wait` how many seconds to wait for its health check.

## How it is built

- **NestJS 12 on Node's own `node:http`** (§5.2), through its `NodeAdapter`, in TypeScript compiled by `tsc` to `dist/`. Once the server reads JSON bodies, the adapter's parser refuses those that try to change object prototypes. NestJS needs TypeScript's decorators and their type metadata, so this package's `tsconfig.json` turns them on over the repository's shared settings.
- **Its own lockfile,** like the apps. Its `.npmrc` repeats the repository's rules: no dependency runs scripts while installing, and the Node.js version is checked.
- **One override:** `@nestjs/platform-node` 12.3.2 pins `qs` at 6.16.0, which GHSA-6pq8-jhm2-2vcw covers, so `package.json` raises it to the patched 6.16.1. Remove the override once a release of the adapter carries the fix.
- **Logs with no clock times:** every line holds a level, the part of the server that wrote it and its message. Requests are never logged, so the logs never show who was active, or when (§6.5, §6.7).
- **Nothing more than asked:** bodies are read as JSON only, and must say their length; a body larger than its route takes (1 MB for a relay upload, a seeding or an observatory's opening, 512 KB for a delivery to the state's stand-in, 256 KB for a school's share of the totals, 64 KB otherwise) is refused before it is read. No header says what the server is built with.
- **Only the web app's pages:** a browser may call the server from the PC web app's own origin, `https://minhajna.djazair.dev`, from the hosted test's own, `https://minhajna-test.djazair.dev` (answer 756), or where the web app is tried locally: `http://127.0.0.1:4180` for `npm run serve` and `http://127.0.0.1:8787` for its Worker under `wrangler dev`, and only with `GET`, `POST` or `PUT` and the headers the demo client sends (`Accept`, `Authorization`, `Content-Type`, `X-World-Pass`). Answers name that origin back, let it read `Retry-After` and vary by origin; none allows credentials, since a world's pass travels in a header, not a cookie. A preflight from any other origin, or for another method or header, is refused with `403` (answer 583).
