# The PC web app's updates (#250, part 4, first pull request)

Checks of 28 October 2026 for the first pull request of part 4 of [#250](https://github.com/djazairdev/minhajna/issues/250), from the pull request that adds this record. It follows [the handover](handover.md). Made-up data, builds and passphrases only.

## What changed

- **Looking for an update (answer 516, R-6.6-06):** at each opening, when the PC is online, the app asks the offline worker for the server's build. The worker fetches `build.json` past every cache and checks its checksum as an install does, then `notes.json`, checked against its line. The version and version code come from `notes.json`, which the checksum covers, and must be the ones `build.json` gives. A build is offered only when the worker finds its version code higher than the installed build's, read from that build's own notes, so no older build, and no other build of the same version, is offered. Offline, before the worker is installed, or on any failure, nothing is offered. `NETWORK.md` says so.
- **The offer (Web-update):** Today shows «تحديث متاح»: the version, what changed in the interface's language, and the new build's checksum beside the current one's, to compare with the published ones. «تثبيت التحديث» installs it; «لاحقاً» leaves the current build running, with a line that the update waits and is offered again at the next opening.
- **Installing:** the worker installs the server's build only if its checksum is the one the teacher saw and it is newer, into a cache of its own beside the current one, every file checked as on the first install. The old cache answers until the new one is whole, and is deleted only then; every page of the app then reloads into the new build, another tab of the app too, its changes already saved. A file that fails its hash, or a server that changed its build meanwhile, leaves the current build as it was. A whole new build left beside the old one, when the worker stopped before dropping the old, is used without fetching it again; a second update for another build is refused while one runs. The page keeps its note of the update even when it stops waiting, so a slow install that finishes is still recorded.
- **After:** the next opening records `app.updated`, a device event with the version and checksum, and only then forgets the note of it, so a reload in between records it once. Today says which version was installed and that the data is as it was, and, once the history holds it, that the activity log has the update, with its day, under the devices. It is recorded while the working copy is on the other device too.
- **Release notes (answer 517):** `apps/web/release-notes.json` holds at most five short lines in Arabic, French and English for one version. The build writes them into `notes.json`, among the files the checksum covers, only when they were written for the version it builds; otherwise the offer has the version and checksum alone. The release guide says when to write them.
- **A new web-only module, Update,** null on the phone, as Browser is, so a phone draws no update card and reads no build facts for one. The worker answers two messages, `check` and `update`; it never changes between builds, as before.
- **Code:** `layerOf` puts every device event in the device layer through `isDeviceEvent`, as it does share events.
- **Words:** every new text in Arabic, French and English.
